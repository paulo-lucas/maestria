# Maestria hosted protocol

Status: implemented by `v2-cloud`. Keep this file in sync with `internal/relay`, `internal/devices` and `internal/cloud`. It is the contract between four parties:

- the **browser** (the Maestria web app, served by the cloud),
- the **cloud** (`maestria-cloud`, multi-tenant, behind a reverse proxy or tunnel),
- the **connector** (`maestria connect`, on the user's machine, outbound connection only),
- the **user**, who approves devices on the machine itself.

Companion docs: `docs/v2-spec.md` (decisions), `docs/v2-architecture.md` (overview), `docs/protocol.md` (Maestro CLI).

## 1. Trust model

**The connector is the authority.** The cloud is an untrusted relay for everything that matters:

| Party | Trusted for | Not trusted for |
| --- | --- | --- |
| Connector | Everything on its machine: data, policy, allowlist, kill switch | n/a |
| Browser device key | Signing requests the user makes | n/a (non-extractable key) |
| Cloud | Accounts, sign-in, presence, routing | Forging a command, reading workspace data at rest, reaching a route outside the connector's allowlist, choosing device keys |

Consequences, each covered by tests:

1. **A relayed request is only executed if a device approved on that machine signed exactly those bytes** (method, path, query, body hash, connector id, device id, timestamp, nonce). A cloud that changes anything, replays, or invents a request is refused by the connector.
2. **The cloud stores no workspace data.** Accounts, 2FA, linked connectors (id, name, hashed credential, last seen, version, OS), paired-device public keys per connector (display only), pending link codes, and an account audit log. Relayed bodies are never logged or persisted.
3. **Live mirror.** An offline connector's workspaces vanish from every view and nothing is queued. A request for an offline connector fails at once (`503 connector_offline`).
4. **Local kill switch.** While it is on, the connector refuses every relayed request (`kill_switch`). Only the local CLI turns it off.

Known limit (inherent, not fixable by protocol): the cloud serves the frontend JavaScript. A compromised cloud can serve hostile JS to a browser that already holds an approved device key and use that key while the page is open. Mitigations are connector-side: allowlist, per-device rate limit, short device sessions (absolute and idle limits), the kill switch, the local audit log, and device revocation from the machine.

## 2. Identifiers, encodings, keys

- All binary values in JSON are base64url without padding (`b64u`).
- **Connector id**: `cn_` + 16 random bytes as lowercase hex (35 chars). Public, appears in URLs.
- **Connector credential**: `mc1.<connectorId>.<secret>` where `secret` is 32 random bytes `b64u`. The connector stores it (0600, `cloud.json` in its config dir). The cloud stores only `sha256(secret)` hex and compares in constant time.
- **Device key**: ECDSA P-256, generated by WebCrypto with `extractable: false`, kept in IndexedDB as a `CryptoKey`. The public key travels as **SPKI DER** (`b64u`).
- **Device id**: `hex(sha256(spki))[0:32]`. It is derived from the public key, so the cloud cannot attach a different key to an id. The connector recomputes it and rejects a mismatch.
- **Signature**: ECDSA P-256 over SHA-256, **IEEE P1363** encoding (`r || s`, 64 bytes), `b64u`. This is what WebCrypto `subtle.sign({name:"ECDSA",hash:"SHA-256"})` outputs. The connector verifies with `ecdsa.Verify` after splitting `r`, `s`.
- **Nonce**: 16 random bytes `b64u` (22 chars). Accepted length 16 to 64 chars of `[A-Za-z0-9_-]`.
- **Timestamp**: Unix milliseconds, decimal.

## 3. Accounts (cloud only)

Hosted accounts reuse `internal/auth` primitives: argon2id hashes, RFC 6238 TOTP (SHA-1, 6 digits, 30 s, ±1 step, replay-protected), recovery codes (`xxxx-xxxx`, argon2id-hashed, single use), the failed-login limiter, token hashing. Sessions, pending logins and codes are per user in the cloud database.

### 3.1 Sign-up

1. `POST /signup` (email, password ≥ 12 chars). The response is always the same "Check your email" page, whether or not the address is already registered (no enumeration). A new account is stored unverified with an argon2id hash and a verification token (30 min, single use, stored as sha256). An existing verified account gets a notice email instead. An existing unfinished account gets a fresh verification email and keeps its original password.
2. The email link is `GET /verify/<token>`. It renders a confirmation form and **consumes nothing** (mail scanners prefetch links). `POST /verify/<token>` with the password consumes the token, marks the email verified and issues a short-lived **setup cookie** (30 min, bound to the user) that is valid only for step 3.
3. `GET /signup/2fa` generates a TOTP secret (held encrypted in the setup record) and shows a QR code and the key. `POST /signup/2fa` with a correct code stores the secret (AES-256-GCM under the server key), creates 10 recovery codes, creates the real session and shows the codes **once** in that response. **An account without 2FA can never log in**: login requires a stored TOTP secret.
4. `POST /signup/continue` (email + password) re-issues the setup cookie to a verified, un-enrolled account (the "continue here" link). All failures give one generic message.

### 3.2 Login (no oracle)

Same shape as local mode. Step 1 `POST /login` (email + password) always runs one argon2id verification (a dummy hash if the email is unknown), stores the verdict server-side in a pending login bound to the IP, and always moves on to the 2FA page. Step 2 `POST /login/2fa` (TOTP) or `/login/recovery` succeeds only if the remembered password verdict **and** the code are good. Every other combination fails identically, ends the pending login and counts as one failed attempt. A disabled or unverified account fails exactly like a wrong password.

Rate limiting and lockout use three scopes: per IP, per account key (a hash of the claimed email, applied to non-existent emails too), and global. While a scope is locked even correct credentials are refused (`429`, `Retry-After`).

### 3.3 Password reset

`POST /reset` (email) always answers "If an account exists we sent a link", and sends the mail only if it does. The link `GET /reset/<token>` shows the form (token not consumed). `POST /reset/<token>` takes the new password **and a TOTP or recovery code**. Both must be valid or the attempt counts as a failure. On success the token is consumed, the password is replaced, every session of the user is destroyed, and the connectors of the user are told to forget their paired devices (section 6.5). Reset never disables or weakens 2FA.

### 3.4 Sessions and web hardening

Opaque random cookie token, only its sha256 stored, idle and absolute expiry, `HttpOnly`, `SameSite=Strict`, `Secure` and the `__Host-` prefix when the public URL is https. Every write needs the session CSRF token (`X-CSRF-Token` or `_csrf`) **and** a same-origin `Origin`/`Sec-Fetch-Site`. A Host allowlist (public URL host) answers `421` for anything else. Strict CSP (`default-src 'none'`, `script-src 'self'`, no inline script or style), no CORS headers, `frame-ancestors 'none'`. Proxy headers (`X-Forwarded-For` or `CF-Connecting-IP`) are trusted only when configured.

## 4. Linking a connector

A link code has 8 symbols from `abcdefghjkmnpqrstuvwxyz23456789` (no look-alikes), shown uppercase as `XXXX-XXXX`, valid **10 minutes**, usable **once**. The cloud stores `sha256(normalized code)` only. Redemption attempts are rate limited per IP and globally.

### 4.1 Web shows the code

1. Signed-in user: `POST /api/link/codes` creates a code bound to the user. The page shows it with the command `maestria connect --link XXXX-XXXX`.
2. The connector calls `POST /api/link/redeem` with `{code, host, os, arch, version}`. Unauthenticated, no cookies. Answer: `{accountHint:"y***@example.com", defaultName, token}`. The code is **not** consumed yet. `token` is a one-time confirmation token bound to this redemption.
3. The CLI shows the account hint and asks `Link this machine to y***@example.com? [y/N]` plus the machine name (default: hostname).
4. `POST /api/link/confirm` with `{code, token, name}` consumes the code (atomic `UPDATE … WHERE used_at IS NULL AND expires_at > now`), creates the connector row and returns `{connectorId, credential}` **once**. The cloud keeps only the credential's hash.
5. The web page, polling `GET /api/link/codes/<id>`, shows "Waiting for the connector…" then "Linked".

### 4.2 CLI shows the code

1. `maestria connect` with no credential calls `POST /api/link/start` with `{host, os, arch, version}` and gets `{code, pollToken, expiresAt}`. It prints the code and the URL to enter it at.
2. The user types the code on the "Link a machine" page: `POST /api/link/claim` (session + CSRF) binds the code to the user's account.
3. The CLI polls `POST /api/link/poll` with `{pollToken}` every 2 s. Once claimed it receives `{status:"claimed", accountHint}`, asks for confirmation on the machine, then calls `POST /api/link/poll` with `{pollToken, confirm:true, name}` and receives `{connectorId, credential}` once.

Both modes require machine-side confirmation, so a leaked code alone does not link a machine without someone at that terminal (and in mode 4.1 the code is shown only to the signed-in user). Unlinking: `maestria connect unlink` (calls `DELETE /api/connector` with the credential, then deletes the local credential) or **Revoke** in the web (`POST /api/connectors/<id>/revoke`): the credential is marked revoked, the socket is closed, and later dials get `401`. Both are audited.

## 5. The connector socket

`GET wss://<cloud>/connector` with `Authorization: Bearer mc1.<id>.<secret>`. The cloud verifies the hash, that the connector is not revoked and that the owner is not disabled. Requests carrying an `Origin` header are refused (browsers must never reach this endpoint). One active socket per connector: a new one replaces the old.

Frames are JSON text messages, at most 256 KiB. Liveness: the cloud sends a WebSocket ping every 20 s; either side closes after 60 s without traffic. The connector reconnects with exponential backoff (1 s to 60 s, ±20 % jitter) and stops on `maestria connect` shutdown after sending a normal close.

All messages have `t` (type).

### 5.1 Connector to cloud

| `t` | Fields | Meaning |
| --- | --- | --- |
| `hello` | `proto:1, version, os, arch, name, killSwitch, devices:[{id,label,state}]` | first frame, then on change of `killSwitch` or devices |
| `res` | `id, s, h, b, more` | response head (status, headers) and first body chunk |
| `chunk` | `id, b, more` | following chunks of a response |
| `err` | `id, code, s` | the connector refused or failed the request |
| `pair_challenge` | `pair, r` | answer to `pair_offer` (section 6.2) |
| `pair_state` | `pair, state, code?` | `pending`, `revealed`, `approved`, `rejected`, `expired`, `mismatch` (`code` carries a refusal reason such as `kill_switch`; the pairing code is never sent) |
| `devices` | `devices:[…]` | device list changed (revoked, approved) |

### 5.2 Cloud to connector

| `t` | Fields | Meaning |
| --- | --- | --- |
| `welcome` | `serverTime` | answer to `hello` (the connector logs the clock skew) |
| `req` | `id, m, p, q, h, b, more` | a relayed request (section 7) |
| `body` | `id, b, more` | more request body |
| `ack` | `id, n` | flow control credit: `n` response bytes were delivered to the browser |
| `cancel` | `id` | the browser went away |
| `pair_offer` | `pair, commit, label, ua` | section 6.2 |
| `pair_reveal` | `pair, spki, nonce` | section 6.2 |
| `forget_devices` | `at` | tighten-only: revoke every paired device (section 6.5) |

## 6. Device pairing (per machine)

Each connector decides for itself. Approval happens **on the machine**, never in the web.

### 6.1 Why commit-then-reveal

A short code can only be compared by a human if the attacker (here: a hostile cloud sitting between browser and connector) cannot choose its key after seeing the code. So the code mixes in a random value from the connector that the browser's key was committed to before it existed.

### 6.2 Flow

1. The browser creates the key pair and a random nonce `n` (16 bytes). It sends `commit = b64u(sha256("maestria-pair-commit-v1" ‖ spki ‖ n))` and a `label` ("Safari on iPhone") to `POST /api/pair` (session + CSRF). The cloud creates a pairing (5 min, in memory) and sends `pair_offer {pair, commit, label, ua}` to **every online connector** of the account.
2. Each connector stores a pending pairing (max 5 pending, 5 min TTL, none while the kill switch is on), generates `r` (16 random bytes) and answers `pair_challenge {pair, r}`.
3. The browser polls `GET /api/pair/<pair>` (or follows the presence stream) and, for each connector that answered, computes its code and reveals the key: `POST /api/pair/<pair>/reveal {connectorId, spki, nonce}`. The cloud sends `pair_reveal {pair, spki, n}` to that connector.
4. The connector checks `sha256("maestria-pair-commit-v1" ‖ spki ‖ n) == commit`, that `deviceId = sha256(spki)[0:32]`, and that `spki` parses as a P-256 public key. Any failure → `pair_state mismatch`. Otherwise it computes the **code**.
5. **Code**: `d = sha256("maestria-pair-sas-v1" ‖ spki ‖ n ‖ r)`; take the first 4 bytes as a big-endian `uint32`, `mod 10^6`, zero padded to 6 digits, shown as `47 · 12 · 86`. The browser computes the same value, so each machine row on the waiting screen shows its own code.
6. The user compares and runs **`maestria devices approve <code>`** on that machine. The CLI accepts only a code of a live, revealed pairing. Typing the code the browser shows *is* the comparison. `maestria devices pending` lists them, `reject <code>` drops one.
7. On approval the connector stores the device (`id`, `spki`, `label`, `approvedAt`), sends `pair_state approved`, and the waiting screen turns that row to "Approved". From now on the browser may sign requests for that connector.

Why a hostile cloud cannot win: it must give the connector a commit for *its* key before it sees `r`, and the user's browser computes its code from the *real* key, nonce and the same `r`. Matching codes then happen with probability 10⁻⁶ per attempt, and the attempt is visible as a pending request the user does not approve. A wrong code typed on the machine simply finds no pairing.

### 6.3 Re-approval and expiry

A device keeps working for the connector's **session policy**: absolute lifetime since approval (default **30 days**) and idle limit since last use (default **7 days**). After either, requests get `approval_expired` / `idle_expired`, the device moves to `expired`, and the browser repeats pairing (same key, new approval). Both limits are configurable on the machine (`relay` section of `config.json`), never from the web.

### 6.4 Revocation

`maestria devices revoke <id>` on the machine, or a signed `POST /api/devices/<id>/revoke` from any approved device (tightening only). Revoked devices are refused immediately (`device_revoked`) and open streams of that device end within 15 s.

### 6.5 After a password reset

The cloud sets `forget_devices_at` on the user's connectors and sends `forget_devices` to those online (the rest get it at their next `hello`). The connector revokes **all** devices, so browsers must be approved again. This can only tighten: a hostile cloud can annoy the user this way but never gain access.

## 7. Relayed requests

Browser to cloud: `https://<cloud>/c/<connectorId>/<path>?<query>`, with a cookie session, CSRF token on writes, and these headers:

| Header | Value |
| --- | --- |
| `X-Maestria-Device` | device id |
| `X-Maestria-Ts` | timestamp, Unix ms |
| `X-Maestria-Nonce` | nonce |
| `X-Maestria-Body` | `hex(sha256(body))` (of the empty string when there is no body) |
| `X-Maestria-Sig` | signature `b64u` |

`path` is the connector-relative path (`/api/inbox`), `query` the raw query string exactly as sent.

### 7.1 Canonical signing string

The browser signs these UTF-8 lines joined by `\n` (no trailing newline):

```
maestria-relay-v1
<connectorId>
<deviceId>
<METHOD>
<path>
<rawQuery>
<bodySha256Hex>
<tsMillis>
<nonce>
```

`METHOD` is upper case. `path` starts with `/`, is the percent-encoded path as sent and contains no `//` or `..` segment. `rawQuery` has no leading `?` and may be empty. No field may contain a control character or a space. The connector rebuilds the string from what it **received** plus its **own** connector id, so a signature for connector A is useless at connector B, and any change of method, path, query, body or timing breaks it.

### 7.2 Connector gate (order matters; first failure wins)

1. **Kill switch** on → `kill_switch` (403). Relay disabled in config → `relay_disabled`.
2. **Shape**: method in {GET, POST}, safe path, header sizes, body ≤ 64 KiB → `bad_request` / `too_large`.
3. Signature headers present → else `unsigned` (401).
4. Device known → else `unknown_device` (403); `revoked` → `device_revoked`; `expired` → `approval_expired`.
5. Timestamp within **±60 s** of the connector clock → else `stale_timestamp`.
6. Signature valid for the device key → else `bad_signature`.
7. `sha256(received body)` equals `X-Maestria-Body` → else `body_mismatch`.
8. **Nonce replay**: `(deviceId, nonce)` not seen within the window (kept 2 × 60 s in memory, bounded 50 000 entries, **fails closed** when full) → else `replay`. Recorded only after the signature verified, so unauthenticated traffic cannot fill it.
9. **Session policy**: approved less than *absolute* ago (`approval_expired`) and used less than *idle* ago (`idle_expired`). On success `lastUsedAt` is refreshed (at most once per 30 s).
10. **Allowlist** (section 8) → else `route_forbidden` (403).
11. **Rate limit** per device (default 120 requests/min, writes counted double) → `rate_limited` (429).
12. Execute the same handler as local mode. Writes are recorded in the connector's own audit log (`relay_write`: device id, method, path, status; never bodies).

Every refusal is audited locally (throttled) and returned as `err {code}`; the cloud passes it on as JSON `{"error":"<code>"}` with the status in the table:

| code | status |
| --- | --- |
| `bad_request` | 400 |
| `unsigned` | 401 |
| `bad_signature`, `body_mismatch`, `unknown_device`, `device_revoked`, `approval_expired`, `idle_expired`, `stale_timestamp`, `replay`, `route_forbidden`, `kill_switch`, `relay_disabled` | 403 |
| `too_large` | 413 |
| `rate_limited` | 429 |
| `connector_offline` (cloud) | 503 |
| `connector_busy` (cloud, too many in flight) | 503 |
| `gateway_timeout` (cloud) | 504 |

The cloud also returns `401`/`403` for its own session and CSRF failures, as JSON `{"error":"unauthenticated"|"csrf"}`.

### 7.3 Multiplexing, size limits, timeouts, backpressure

- Requests are multiplexed over the one socket by `id` (`r_` + 8 random bytes hex). At most **32 in flight** per connector and **8 streams** per browser session (`connector_busy`).
- Request body ≤ 64 KiB (chunked into `body` frames of 32 KiB). Non-streaming responses ≤ 8 MiB, otherwise `err too_large` and the request is aborted. Header block ≤ 8 KiB.
- The cloud waits 30 s for the response head and 60 s overall for non-stream requests (`gateway_timeout`), then sends `cancel`.
- **Flow control**: the connector may have at most 256 KiB of response bytes unacknowledged per request. The cloud sends `ack {id, n}` after writing `n` bytes to the browser. A slow browser therefore pauses the connector's handler (its writes block) instead of growing memory anywhere. If the browser disconnects the cloud sends `cancel` and the connector cancels the handler's context.
- **Live stream**: `GET /api/stream` (SSE) is one signed request whose response never ends. The connector re-checks the device (revoked, expired, kill switch) every 15 s and ends the stream when it no longer passes. Each browser session holds one stream per connector.
- The cloud passes through only these response headers: `Content-Type` (from a small allowlist), `Cache-Control: no-store`, `Content-Disposition`, `Retry-After`. It sets its own security headers on the response and adds `Content-Security-Policy: sandbox` so a relayed HTML body can never run as a page of the cloud origin.

## 8. Relay allowlist (connector side)

Only the browser routes the UI needs. Anything else is `route_forbidden`, even with a valid signature. Path wildcards match exactly one segment.

| Method | Path |
| --- | --- |
| GET | `/api/workspaces`, `/api/inbox`, `/api/workspaces/*/inbox`, `/api/workspaces/*/chat`, `/api/workspaces/*/activity`, `/api/workspaces/*/floors`, `/api/workspaces/*/docs`, `/api/floors`, `/api/wire`, `/api/usage`, `/api/stream`, `/api/audit`, `/api/relay/info`, `/api/devices` |
| GET (HTML views) | `/`, `/workspaces/*/tasks`, `/workspaces/*/chat`, `/workspaces/*/activity`, `/workspaces/*/floors`, `/workspaces/*/docs`, `/workspaces/*/docs/asset`, `/usage` |
| POST | `/api/inbox/dismiss-notices`, `/api/workspaces/*/inbox/dismiss-notices`, `/api/workspaces/*/inbox/*/respond`, `/api/workspaces/*/inbox/*/dismiss`, `/api/workspaces/*/inbox/*/postpone`, `/api/workspaces/*/chat`, `/api/workspaces/*/agents/*/approve`, `/api/workspaces/*/agents/*/reject`, `/api/workspaces/*/agents/*/prompt`, `/api/standby/config`, `/api/standby/resume`, `/api/devices/*/revoke`, `/api/kill-switch` |

Never reachable through the relay: login and logout, `auth setup`, sessions, the kill-switch **reset** (`maestria tunnel on` is local only and has no HTTP route), config writes (workspace registry, Wire pairing, tunnel commands), device **approval**, and everything not listed above. `POST /api/kill-switch` only turns the switch **on** (tightening).

Relayed requests run the same handlers as local mode behind a relay gate instead of the local cookie/CSRF/Host checks. They run as a fixed internal session that never reaches the browser.

## 9. Browser transport

One JS layer chooses the transport. Local mode calls `/api/...` with the session cookie. Hosted mode calls `/c/<connectorId>/api/...` after signing. The hosted app:

- keeps one non-extractable key pair in IndexedDB (`maestria-keys`), and the list of connectors it is approved on (`localStorage`, convenience only),
- signs with `subtle.sign`, refreshes the timestamp for every request, uses a fresh nonce,
- fetches connectors from the cloud (`GET /api/connectors`), then calls each online, approved connector,
- renders Overview from the JSON APIs of all online connectors (workspaces from several machines, usage grouped by provider account across machines), and renders the other workspace pages from the connector's own HTML views,
- treats a connector that disappears from presence, or answers `connector_offline`, as gone: its workspaces leave every view at once,
- shows "No machine online" when no connector is online, "Approve this browser" when it holds no approved key on an online machine.

## 10. Cloud HTTP surface

Browser (cookie session, CSRF on writes):

`GET /signup /login /login/2fa /reset /verify/<t> /reset/<t> /signup/2fa /signup/continue`, matching `POST`s, `POST /logout`.
App shell (the same HTML for each, the app routes on the client): `/ /connectors /connectors/link /security /pair /c/<id>/...` (page navigations of workspace views).
JSON: `GET /api/me`, `GET /api/connectors`, `POST /api/connectors/<id>/rename`, `POST /api/connectors/<id>/revoke`, `POST /api/link/codes`, `GET /api/link/codes/<id>`, `POST /api/link/claim`, `POST /api/pair`, `GET /api/pair/<id>`, `POST /api/pair/<id>/reveal`, `GET /api/presence` (SSE: connector online/offline, pairing state).
Relay: `GET|POST /c/<id>/<path>`.

Connector, unauthenticated by cookie (rate limited, no `Origin`): `POST /api/link/start|poll|redeem|confirm`, `DELETE /api/connector`, `GET /connector` (WebSocket).

## 11. Threat model summary

| Threat | Defence |
| --- | --- |
| Stolen password | Mandatory TOTP; recovery codes single use; reset needs 2FA |
| Credential stuffing / brute force | argon2id; per-IP, per-account, global limits and lockout; no oracle |
| Session theft | HttpOnly, SameSite=Strict, `__Host-`, idle + absolute expiry, server-side hash |
| CSRF / cross-site writes | Token + Origin/Fetch-Metadata check on every write |
| DNS rebinding | Host allowlist |
| Hostile cloud forges or edits a command | Device signature over method/path/query/body hash; refused by the connector |
| Hostile cloud replays | ±60 s window, nonce cache that fails closed, connector id in the signed string |
| Hostile cloud swaps a key at pairing | Commit-then-reveal code verified by the user on the machine |
| Hostile cloud reaches other routes | Connector allowlist; no approve / reset / config routes |
| Hostile cloud reads data at rest | The cloud stores none; bodies never logged |
| Stolen browser or phone | Device revoke from the machine or a trusted device; absolute and idle expiry; kill switch |
| Leaked link code | 10 minutes, single use, hashed, confirmation on the machine, rate limited |
| Leaked connector credential | Hashed server-side; revoke in the web; it only lets a machine dial in, it cannot sign for a user |
| Flooding | Frame, body and in-flight limits, per-device rate limit, bounded caches |
| Compromised cloud serves hostile JS | Out of protocol scope; bounded by allowlist, rate limit, short device sessions, kill switch, local audit |

## 12. Implementation notes

- **Where the code is**: `internal/relay` (frames, canonical string, allowlist, pairing math, no I/O), `internal/devices` (connector device store, policy, nonce cache, verification), `internal/connect` (outbound client, relay gate, flow-controlled response writer, link file), `internal/cloud` (server, accounts, hub, relay, UI), `cmd/maestria-cloud`. The browser half is `internal/cloud/static/hosted-keys.js`; a Go test runs it under node and checks its signatures, device id, pairing commitment and code against `internal/relay`.
- **One code per machine**: because each connector contributes its own random value, the pairing screen shows one code per machine (next to its name) instead of one shared code.
- **Kill switch blocks the relay entirely**: a machine with the kill switch on is refused for every request (including reads), so its data disappears from the panel and the Overview shows a "Kill switch is on" state for it. Monitoring a killed machine is deliberately not possible.
- **`/c/<id>/...` is both the page address and the relay address**: a request carrying `X-Maestria-Sig` is relayed; a plain navigation gets the app shell.
- **The Overview is built in the browser** from each machine's own `GET /` view and `GET /api/usage`-style sections (workspaces, tasks, agents, floors, usage), merged per machine. Usage is grouped by provider and account label; a machine name is shown only when the same provider has different accounts on different machines. Other workspace pages are the machine's own HTML views.
- **One process, one lock**: `maestria serve` runs the local panel and, when the machine is linked and `relay.enabled` is on, the cloud connection too (`--connect` insists, `--no-connect` stays local). The relay then serves the very same `web.Server` as the panel: one Wire subscription, one standby guard, one database handle. `maestria connect` is the connection alone. Both take `run.lock` in the config directory (pid, mode, heartbeat; stale after a dead pid or 90 s without a heartbeat), so a second `serve` or `connect` on the same directory refuses with a message. CLI commands (`post`, `say`, `wait`, `devices`, `status`, ...) do not take the lock. A revoked link ends only the connection; the local panel keeps running. Service install modes: `serve`, `connect`, `both` (`maestria serve --connect`).
- **Workspaces with the same name on different machines** are shown as `Name · Machine` in the navigation.
- **Cloud config**: `config.json` in the data dir (0600) plus `MAESTRIA_CLOUD_*` variables; `server.key` (0600) encrypts TOTP secrets at rest.
